# Bridge Calculators: project notes (read this first)

One offline HTML file, `Bridge-Calculators.html`, that replaces the Excel sheets a deck officer uses on board. Works from a double-click, no internet, no server.

## Where things are
- **`Bridge-Calculators.html`** is the source of truth. After every change, copy it to `~/Desktop/Bridge-Calculators.html` (the copy used on board).
- Version control is git, remote `iMariner/imariners-bridge-calculators` on GitHub (public, MIT). **After every finished change: commit with a clear message and push.** The owner asked for everything to stay up to date on GitHub.
- `build/` has the scripts and tests used to build and verify each tool (see "Verification").
- `data/` has the packed data that is embedded in the HTML (special areas, coastline, a comparison table).
- The tools were ported from a macro-free Excel compass error workbook; the maths was checked against astropy.
- Verified special-area coordinates come from `~/Developer/iMariners/sea-areas/data/*.json` (do not retype coordinates, rebuild from there).

## Look and feel
Read `ART-DIRECTION.md` first for any visual work ("Chart table": navy sidebar, white cards, teal brand, ruler under each page title, mono card titles). Every tool page has the same parts: page header, then cards that each start with an `h2` title. Do not invent a new layout. Review screenshots with `node build/tools/shot.js <outDir> [width] [height] [day|dusk|night]` (headless Chrome, example data in every tool) and check print sheets with `node build/tools/printpdf.js <tool-id> <example-button-id> <out.pdf>`. The Design System page has the live tokens and the compliance check.

## Sight Fix (build/sight): in the app since Oct 2026
`engine.js` holds the block `SIGHT-BEGIN/END`: 58 navigational stars (Hipparcos J2000 + proper motion, `cat_j2000.json` is the source), apparent places with precession, nutation and aberration, the Sun from truncated VSOP87D, Hs to Ho (dip, Bennett refraction with T and P, SD, parallax), Hc and Zn. Plan: `docs/PLAN-sight-fix.md` (local). Tests: `node build/sight/test_engine.js` (24 checks incl. Nautical Almanac correction tables), `node build/sight/test_workbook.js` (the owner's CEL NAV.xls example), and the ERFA comparison: `node build/sight/gen_cases.js > /tmp/c.json; python3 build/sight/compare_erfa.py /tmp/c.json build/sight/cat_j2000.json` (needs astropy). Result on 600 random cases: Sun within 0.006', stars within 0.013' (minutes of arc). `fix.js` (block `SIGHTFIX`) is the running-fix solver; tests: `node build/sight/test_fix.js` (316 checks: synthetic round trips, constant error, noon latitude, date line, weak cut, high latitude, brute-force least-squares comparison, rhumb propagation against an independent formula, owner's workbook geometry). Both phases were independently reviewed by Codex and an Opus agent; their findings are fixed. Note: the owner's workbook refraction is about 33% too large because its constant is for pressure in mmHg but it is fed millibars.

## Old browsers (ship PCs never get updates)
The page must work on any Chrome or Edge from version 84 (2020) on, because ship PCs are offline and their browsers are frozen. Rules: no `color-mix()` (use the precomputed `--*-rgb` and `--tint-*` tokens), no `inset:` shorthand, no `:has()`, no modern JS (the script is written in plain ES5 style). A banner appears on older browsers. Test with a real old Chromium: `curl -O https://commondatastorage.googleapis.com/chromium-browser-snapshots/Mac/768968/chrome-mac.zip` (Chromium 84), unzip, `xattr -cr`, then `CHROME=<path>/Chromium.app/Contents/MacOS/Chromium HEADLESS=--headless node build/tools/shot.js <outDir>`. `build/tools/theme-colours.js` prints the theme colours used to precompute the tint tokens.

## How the file is organised
1. `<style>`: first the **DESIGN SYSTEM** (colour tokens now include the sidebar `--side-*`, `--border-strong`, `--matrix-head`) (Geist and Geist Mono embedded as base64, colour tokens for Day / Dusk / Night, type, spacing, radius scales), then component CSS, then one block per tool.
2. `<body>`: header, side navigation (`data-tool-link`), `<main>` with one `<section class="tool" id="...">` per tool. A tool's print sheet is a `.print-sheet` child of its section.
3. `<script>` (one IIFE): `store` (localStorage, key prefix `bridgeCalc.`), `Ships`, the almanac engine (`ASTRO-BEGIN/END`), calculation blocks with begin/end markers (`REPORTS-`, `SUN-`, `GEO-`, `ETA-`, `CALC-`), one `initXxx()` per tool, the embedded data blobs (`SA_AREAS`, `SA_LAND`, `SA_SHEET`), then the `TOOLS` registry and hash routing.

Tools now: True Wind, Meridian Passage, Sunrise & Sunset, Sight Fix, Special Areas & Map, Gyro & Compass Error (includes the true azimuth working), Deviation Card, Course & Speed Made Good, ETA, Vessel Daily Reportings, Draught due to Heel, Safe Anchoring Depth, Ship Particulars, Design System. (True Azimuth still exists at `#true-az` but is hidden from the menu.)

## Rules that must hold
- **Design system only.** No hex colours, font names, px font sizes or px radii in component CSS or inline styles; use `var(--token)` and the `u-*` helper classes. Night theme is red only. After any change open the **Design System** page and press **Run check**: it must say Clean.
- **Saves automatically, like Excel.** Every input goes through `store.get/set` under a `bridgeCalc.` key. Per ship data is keyed by `Ships.active().id`. No download buttons in the normal flow (the owner does not want extra files).
- **Never mark something verified that is not.** Coordinates are exactly as printed in the IMO texts with the source shown; points derived from the coastline are flagged COAST POINT.
- **Wording:** short answers, plain words, no em dashes in anything the owner reads (user rule for iMariners content).
- Every result that a mistake could hurt (sun times, areas, distances) must be tested against an independent source, not only against itself.
- Work in subagents inside one conversation, never separate sessions (global rule).

## How to add a tool
1. Back up. 2. Add the nav link (`<a href="#id" data-tool-link="id">`) and a `<section class="tool" id="id" hidden>` using `.tool-head`, `.grid` / `.tool-layout`, `.card`. 3. Write `initId()` and add it to `TOOLS`. 4. Keep pure maths in a block with begin/end markers so node can test it. 5. Save inputs with `store`. 6. Run the Design System check. 7. Add a one-page `.print-sheet` if the owner would print the result.
The `build/*/patch.py` files show the pattern used so far: a Python script with `assert`ed string replacements that fails safely if the file changed. They were already applied; they are kept as examples only (paths inside point to old temporary folders).

## Known gaps and ideas
- Moon rise and set (only Sun is done). Other sea-areas layers from `sea-areas/data` (piracy HRA/VRA, IBF, JWC) are not in the map yet; the same map can show them.
- Special-area regions are drawn from straight lines between points; North American, US Caribbean and Canadian Arctic ECAs and the Suez box are geodesic in the regulations, difference is small.

## Sight Fix page assembly
Sources are `build/sight/{engine,fix,plot,page}.js`, `page.html`, `page.css`. After editing them run `python3 build/sight/assemble.py` (replaces the section, CSS and script blocks in `Bridge-Calculators.html`; edit the sources, not the HTML). `plot.js` (`SightPlot`, test `node build/sight/test_plot.js`) draws the SVG plot used on screen and on the one-page A4 sheet (`#sf-sheet`). Check the sheet with `node build/tools/printpdf.js sight-fix sf-example /tmp/sf.pdf` (must be 1 page). All phases reviewed by Codex and Opus; fixes applied. Time zone rule is the same in every tool since 25 Oct 2026: ship's time zone as a UTC offset, East + ("+8 means ship's time = UTC + 8"). True Azimuth and Meridian Passage saves older than that (no `zs: 2`) are negated on load. Known and accepted: rows typed out of order across midnight are not re-dated; print CSS uses plain colours like the other print sheets. One sight on its own gives a position line (`SightFix.single`): intercept, ITP, longitude by chronometer, or the latitude at the DR longitude when the body bears within 30 degrees of N or S (Polaris, Sun near noon). Under each Hs box `expectRows` (page.js) shows the expected sextant altitude and Zn from the row DR ("≈ 38°02.2' · Zn 006°"); when the reading is far off it says "Hs should be about X" (amber over 20', red over 60'; red "below the horizon" too), so a wrong body, time, date or zone is seen before solving. `read()` warns (does not block) when the zone is more than 2.5 h from longitude/15, and the error message repeats that hint. Tests: `test_single.js`, `test_reject.js` (impossible sights are refused: intercept over 180' (3 degrees), or a line missing the fix by over 10' when the misses are not one common error).

## Earth model (since 25 Oct 2026)
`WGS84` block (`WGS84-BEGIN/END`, source `build/geo/wgs84.js`, test `node build/geo/test_wgs84.js`): exact rhumb line (isometric latitude and meridian arc) and Vincenty geodesic on WGS84, as ECDIS. `courseMadeGood` (Course & Speed) uses it, so there is no jump near 090/270 any more. Checked: Vincenty's published example to 0.01 m, rhumb against numerical integration within 0.01 NM, course within 0.05 degree of Norie meridional parts.

## Moon and planets in Sight Fix (since 25 Oct 2026)
`engine.js` block `BODIES-BEGIN/END` is generated by `python3 build/sight/gen_bodies.py <dir> build/sight/engine.js` from the IMCCE VSOP87D files (Venus, Mars, Jupiter, Saturn, truncated, scale 6) and the Meeus ch. 47 Moon table (soniakeys/meeus, MIT). `Sight.place(ms, name)` gives any body; `Sight.reduceBody(place, lat, lon)` works the Moon topocentric (WGS84 observer), so the Moon's parallax and the Earth's shape are inside Hc and Ho gets only dip, refraction and the topocentric semi-diameter; planets get parallax HP cos Ha and no semi-diameter. Checked against JPL DE440 (`ref_bodies.py`, `ref_topo.py`; need astropy + jplephem + de440s.bsp): planets within 0.032', Moon geocentric 0.05' typical, 0.16' worst (the Meeus limit; the Almanac prints to 0.1'), Moon topocentric Hc within 0.11', and 191 three-body fixes with the Moon's altitude taken from DE440 all within 0.08 NM. Offline tests: `node build/sight/test_bodies.js build/sight/de440_bodies.json`, `node build/sight/test_moon_planets.js build/sight/de440_moon_topo.json`.
The working table shows the Moon the Almanac way (geocentric LHA and Hc, "Parallax in altitude" = geocentric Hc minus observer Hc, added to Ho), so a hand check adds up; the intercept is identical (Opus checked 8701 sights: within 0.005' of the full Almanac method with oblateness). The second mode is "All bodies" (Sun, Moon, planets, stars), so a Sun + Moon or Sun + Venus day fix can be entered; the limb choice shows for the Sun and the Moon.

## Checked against the textbook (25 Oct 2026)
"Principles of Navigation" (Capt. T.K. Joseph and Capt. S.S.S. Rewari), chapter 11 (book page = PDF page - 9). The intercept method (DR used as the assumed position, Towards when TZD < CZD), longitude by chronometer (the line crosses the DR latitude), ex-meridian (latitude where the line crosses the DR longitude) and Polaris all match the app. The book works a second sight either from the original DR (example 9) or from the DR carried forward (example 10); Sight Fix offers both ("Work every sight from: DR at each sight / The first DR", `inp.apMode`), the fix is identical, only the working changes (`test_apmode.js`). `test_book.js` checks the engine against the 1976 Almanac figures quoted in the chapter (one book misprint noted).

## Sunrise & Sunset: Moon and a moving ship (since 25 Oct 2026)
`SunTimes.solve(y, m, d, zone, lat, lon, hoe, mv)`: `mv = { course, speed, ms }` moves the ship on a rhumb line from the position given for time `ms`; every event is solved at the ship's position at that moment. Moonrise/moonset (upper limb on the visible horizon, topocentric, using `Sight.moonPlace`/`reduceBody`) and the lit fraction are in `R.moon`. Test: `node build/sun/test_moon_moving.js` (59 moon events against JPL DE440, worst 0.6 s; `ref_moonrise.py` makes the reference). `build/sun/*` were re-synced from the HTML (edit the HTML, then re-extract). Meridian Passage shows "Before noon": the time of mer pass at the DR and the sextant altitude to preset (inverse of the Sight engine corrections).

## Textbook check, chapters 8, 9 and 12 (25 Oct 2026, Opus)
All altitude-correction examples (Capella, Mars, Sun UL, Moon LL) match to 0.0'; time chapter within 2 s; moonrise examples within 0.7 min. Differences come from the book's table approximations (refraction at or below 0 degrees, amplitude example) or book slips (Ex 5 Moon parallax with true instead of apparent altitude; Exercise XII 4 answer copied from question 3). ## Sight methods picker (since 25 Oct 2026)
Sight Fix opens with "Method: what did you observe?": Noon position, Sun running fix, Position line / long by chron, Meridian altitude / ex-meridian, Pole Star, Star fix, Sun + Moon or Venus. Each sets the internal mode (`sun` or `stars`), fills body names only into rows that have no altitude yet, and shows a one-line how-to (`METHODS` in page.js, `st.method` saved). "Give the fix at (ship's time)" sets `inp.fixMs` (Noon position fills 12:00, as Subramaniam ch. 26 gives the noon position at 1200 ST). Checked against Capt. H. Subramaniam, Practical Navigation (2010), ch. 26 worked example: `node build/sight/test_subramaniam.js` (longitude by chronometer, noon position and the sextant meridian altitude all within 0.3'; `anyYear: true` lets tests use the book's 1992 dates).
Also `node build/sight/test_subramaniam_examples.js`: 26 worked examples from Subramaniam ch. 10, 14-18 and 24 (Sun, stars, Polaris, planets, Moon, ex-meridian, below the pole, combination fixes), 96 checks, all within 0.35' (largest 0.28'). Not in the app on purpose: back-angle sights; altitude-only circumpolar problems (no time).

## DR at each sight (since 25 Oct 2026)
Every sight row has "DR at this sight" (any format Geo.parse reads, e.g. 21 22.2N 037 57.2E). Empty: worked from the first DR, course and speed and shown in grey; "Fill DR positions" writes those in to check or change. `SightFix.fix` uses `sight.dr` when given: each sight is reduced from that position and the lines are carried to the fix time by the movement between the officer's positions (`own` path in fix.js; test `test_owndr.js`). `node build/tools/smoke.js` (headless Chrome, every tool and every Sight Fix method) must pass after every change: it would have caught the `ft is not defined` break shipped in d8a62a8.

## Sight Fix: stars panel and easy positions (since 25 Oct 2026)
"Stars and planets you can take" (in the Sights card, All bodies mode): time from its own field or the first sight; Morning / Evening twilight set it halfway between nautical and civil twilight (SunTimes). Chips list stars and planets 15-70 deg (GOOD: 20-60 deg and mag 2.0 or brighter), with altitude, bearing and brightness; tapping one puts it in the next empty row; "Use the best 4" calls `Sight.suggest` (now 20-60 deg, spread in azimuth). The Sun's altitude decides the light note. Positions per sight are read by `parsePos` in page.js: 2122.1N 03757.1E, 21 22.1N 037 57.1E, 21-22.1N, lower case, or no letters (DR hemispheres); tidied to 21°22.1'N 037°57.1'E on leaving the box. The plot numbers each sight's DR point 1, 2, 3...
Examples (since 25 Oct 2026): "Load example" fills every box for the chosen method (`exampleSights` in page.js): sights are generated from a known true track (060 deg 14 kn, 22 54N 090 24W area, zone -6, 15 Jan 2026 or 10 Jan 2026 for Sun + Moon), DR 3' S and 4' E of the truth, so every example's fix comes out 5.0 NM on 307 deg from the DR. smoke.js checks all 7 examples show a fix and a diagram. The body drop-down starts with "Good now (altitude, bearing)" from the stars panel, then Sun, Moon and planets, then all stars A to Z.
Plot (since 25 Oct 2026): drawn as by hand: from each assumed position the azimuth (dotted arrow), the intercept (red, towards or away) and the position line at right angles through the ITP (dashed); solid = carried to the fix time. The view includes every crossing of the lines, so the whole cocked hat is shown. Body list: "Good now" only, plus "Show all..." which gives that row the full list. A sight more than 3 degrees from the DR is named before solving; if the solver cannot settle, the sight that fits least is named.
Diagram key and views (since 25 Oct 2026): a key with a sample of each line sits under the diagram (`plotKey` in page.js, also a one-line key on the print), and "Diagram: With the working / Clean" (`opt.clean` in plot.js) hides the construction. `SightPlot.geom` holds the geometry; `node build/sight/test_plotgeom.js` checks it (intercept laid off along the azimuth, position line at 90 deg, solid = dashed moved by the run, fix on every line within its residual).
